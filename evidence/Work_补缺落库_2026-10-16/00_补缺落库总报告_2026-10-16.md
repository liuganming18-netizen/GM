## 二、落到哪里（关键设计）

数据分两层，**冷层是全量历史，热层只是近 34 天滚动窗**：

```
冷层  数据/市场数据/parquet/candles/{交易所}/{市场}/{标的}/{周期}/{年}.parquet       ← 明细（全版本）
      数据/市场数据/parquet/candle_heads/{交易所}/{市场}/{标的}/{周期}/{年}.parquet  ← 头索引
热层  数据/市场数据/db/market_v2.sqlite3  的 candle_versions + candle_heads（近 34 天）
```

读侧 `MarketDataRepository._cold_candles` 用
`candles JOIN candle_heads USING(交易所,市场,标的,周期,open_time,source_id)` 取头版本 ——
**所以两个目录必须成对写入，且 `source_id` 一致**。

**本次落点 = 冷层，只写新文件：**

```
数据/市场数据/parquet/candles/.../{年}_补缺20261016.parquet
数据/市场数据/parquet/candle_heads/.../{年}_补缺20261016.parquet
```

- **既有分片一个字节都没改**（`{年}.parquet` 原样不动）。
- 新增分片 **188 个**（94 个「组合×年」× 2 个目录），共 7.4 MB，**120,680 行**。
- `sources` 表新增 **80 行**（每个组合一行）登记来源，共 120,680 根。
- 热层 sqlite 的 `candle_versions` / `candle_heads` **一行没动**（近 34 天滚动窗语义不被污染）。

**为什么不用 sqlite**：`candle_versions` 是热层，往里塞 2022 年数据违反分层设计，将来归档器下沉时会重复。
冷层才是全量历史的归属地。

## 三、回滚方法（三步，可精确执行）

1. **删新增分片**（188 个文件，共 7.4 MB）：
   `find 数据/市场数据/parquet -name "*_补缺20261016.parquet" -delete`
2. **删 sources 登记**（80 行 / 120,680 根）：
   ```sql
   DELETE FROM sources WHERE file_path LIKE '%20261016_补缺';
   ```
   > ⚠️ **不要按 id 区间删**。本批 id 落在 6/7/8/9/10/12 百万段，但采集器/下载器随后自增
   > 的行也落在同一区间（实测同区间内另有 2,755 行非本批）。必须按 `file_path` 精确匹配。
3. **恢复记账表**：把 `backup_coverage_cache_2026-10-16.csv`（落库前全量）
   或 `backup_coverage_cache_apply_*.csv`（每次重建前）导回 `coverage_cache`

`_catalog.json` 备份在 `数据/市场数据/parquet/_catalog.json.bak_补缺前_20261016`。

> 全部为「新增文件 + 新增 sources 行 + 覆盖记账表」操作，无一处改写既有 K 线分片
> ⇒ 回滚即删文件，不留残渣。
