## 7 未解决项 / 边界内报告

### 7.1 未解决（如实列出，未修复）

1. **历史 375 个 run 的 `chart.json` 仍是旧格式**（数组 candles、`signals: []`、`funding_events: []`、`trade_id: null`）。
   本轮按边界**未回写历史产物**（原件 mtime 已断言未变）。显示靠**读取侧** `_backfill_chart()` + 前端 `normalizeCandle()` 兜住。
   ⇒ 若将来有人绕过 `_backfill_chart` 直接读盘（例如新写一个脚本直接 `json.load(chart.json)`），会重新看到空 `signals`。
2. **资金费事件的 `rate` / `mark_price` 为 `null`**：账本 `funding.jsonl` 的 `FUNDING_FEE` 只落 `delta`/`fee`，未落费率与标记价。按「缺就 `None`，不用 `0` 冒充」保持 `null`，页面显示 `—`。要补齐必须改采集/执行落盘，属边界外。
3. **六笔的 `stop_trace` 都只有 1 个 `init` 点**：这是账本事实（无后续止损调整），不是显示缺陷。按任务书「没有后续止损调整时如实显示，不能合成轨迹」，图上不画止损线。
4. **`backtest_store.new_trade_id()` 仍以 run_id 为种子，且仍在被调用** —— 调用点是 `backtest_runner._run_event_trend()` 第 999 / 1033 行，属**写入侧**（回测引擎生成账本时用它给交易编号）。这是合法的：写进 `positions.jsonl` 的 `POSITION_CLOSED.payload.trade_id` 就是它算出来的，**账本里那个值就是权威值**。
   缺陷只出在**读取侧拿目标 run_id 去复算**（批量脚本「引擎在自己 run 目录跑完再复制产物到脚本 run 目录」⇒ 目标 run_id 复算必然对不上：LPT 复算得 `trd_9d6019a5e43ab100`，账本真值 `trd_eb941d2defdde27285ef06e2`）。**所有读取侧复算已删除**。
   残留提醒：若将来有人再写「用 run_id 复算 trade_id」的代码，会重新产出错 id。
5. **`orders.jsonl` 本身不落 `trade_id`**（实测首行只有 `order_id`/`signal_id`/`client_order_id`），`trades.jsonl` 也不落 `trade_id`（只有 `order_id`/`exit_order_id`）。因此订单↔交易的关联只能由 `trades.order_id` / `trades.exit_order_id` 与 `orders.order_id` 精确匹配得出——这正是 `ledger_links.py` 的做法。**账本 schema 缺 `trade_id` 是既有事实，本轮未改账本（边界）。**
6. **`backtest_runner.py:1046` 平仓单的 `trade_id` 用 `last_entry[sym]`（该标的最近一次开仓）推出**，属状态/顺序推导，不是 id 直连。在「单标的单持仓」的引擎语义下结果确定且正确，但性质上仍是顺序推。由于 `orders.jsonl` 实际未落该字段，本轮未改动它（改了会动写入侧，超出边界）；如需彻底消除顺序依赖，建议后续把 `trade_id` 直接写进 `orders.jsonl`。
