## 2. 运行器与桥（backtest_runner.py / oi_resonance_bridge.py）

### 2.1 运行器职责边界（正面）
`backtest_runner.py` **不自建撮合/止损/资金费/仓位**，只做：取数 → 组装 → 调候选包唯一执行核心 `run_portfolio_execution` → 落账 → 指标/基准/图表/质量。这与项目「唯一执行核心」纪律一致，杜绝了「回测与实盘两套逻辑」。

关键实现要点（均已核实）：
- 分页取满：`_fetch_candles_all` 逆序翻页直到取尽，超过 `CANDLE_HARD_CAP=20000` **抛错而非静默截断**。
- 覆盖校验：`_closed_contiguous` 同时判「首根==start、末根+iv==end、实际根数==期望根数」，能发现「空窗 / 尾段被截 / 整段缺失」——仅查相邻差是不够的，这里补上了。
- 预热不足**拒绝运行**（不静默缩窗）：`actual_warm < need_warm` ⇒ 抛错。
- 资金费覆盖判据：不依赖 `actual >= expected`（欠算的 expected 会恒真），而是**逐网格点**核验每个「应有结算时刻」都有真实事件命中（容差 60s，含窗口左端点）。
- 指标**从账本独立重算**（`recompute_metrics_from_ledger`）再与引擎侧逐项对账（`_metrics_match`），不等即判 degraded。
- 缺 OI 记 `NaN`、缺资金费字段记 `funding_gap`，**一律不用 0 / 0.5 冒充**。

### 2.2 桥（oi_resonance_bridge.py）职责边界（正面）
- 本文件**不含任何策略数值**，阈值唯一来源是候选包 `config`。
- 候选包/numpy 不可用 ⇒ `AVAILABLE=False` + `IMPORT_ERROR`，调用方置 failed，**不退回默认参数**。
- 参数白名单 + 作用域拆分（`split_params`）：`fee_rate/slippage_bps/initial_equity` 属 exec 作用域，不会混进 signal 参数被静默丢弃。
- `code_hash()` 覆盖范围 = 候选包全部 `.py` **+ 后端 4 个文件**（桥/运行器/存储/API）。这一点很关键：只哈希策略包会漏掉「后端改动改变结果」。实测该哈希与 golden 一致。
- 窗口校验：显式窗口须对齐 15m 网格、跨度 ≥1 天、与 `window_days` 互斥、**不静默取整**。

### 2.3 运行器的一个已知口径差（不判失败，但需知晓）
`load_inputs` 取信号序列的右端点是 **`win["sig_end_ms"]`（= 数据末端，最后已收盘 bar）**，而**不是 `win_end`**。也就是说：**信号序列会一直拉到"当前数据末端"**，比交易窗口更长。

- 影响：交易窗口由 exec 序列（严格 `[win_start, win_end)`）钉死，窗口外的信号经 `searchsorted` 落到 `j >= n15` 被跳过 ⇒ **不影响交易结果**。
- 风险：若行情库在两次运行之间增长了，信号序列长度就变，`signal_bars.csv` 快照哈希随之变。这正是 golden 记录的「已知口径差」的根因（见 §11-发现3）。

## 3. 执行核心（oi_resonance_v1/execution.py）

### 3.1 同一根 bar 的固定相位（正面）
每根执行 bar 严格按相位推进：
```
A 开盘：① 锁利生效  ② 资金费结算
B 开盘：跳空退出（**只用 open**）
C 开盘：新开仓（用本 bar open；取整后再算风险/止损）
D bar 内：止损检查（**含当根刚建立的仓位**）
E 收盘：盯市与权益
```
这个顺序杜绝了两类常见 bug：
- 「用未来 low 提前释放资金」（相位 B 只用 open）；
- 「新开仓当根不检查止损」（相位 D 明确包含当根新仓）。

### 3.2 已修复的硬伤（源码注释可证，已核实实现）
1. 费用率不再硬编码（旧稿 `_compute_unrealized_pnl` 写死 0.0005，与 `cfg.fee_rate` 脱钩）。
2. 入场费只记一次（开仓 `cash -= entry_fee`；未实现只估**出场**费）。
3. 资金费起算点 = 入场毫秒（旧值 `-1e9` 会给新仓补收开仓前全部历史资金费）。
4. 资金费判据用**毫秒** `last_funding_ms < ev_ms <= t_ms`（旧 `//1000` 截秒会漏掉「开仓后数毫秒」的真实结算）。
5. 保护止损轨迹 `stop_trace` 实况记录（不重建、不造点）。

### 3.3 期末处理（正面）
`force_close_at_end=true` ⇒ 期末强平，`equity_curve[-1]` 与 `final_equity` 强制一致（`equity_curve_tail_matches_final`）。实测 `final_equity = 96918.59176552141`，`unrealized_net_open = 0`。

## 4. 数据读取链（market_repository.py）

路由：**热层 SQLite（近 30 天，保证 latest200）+ 冷层 DuckDB/Parquet（全量历史）**。

审计要点：
- **头版本语义**：无 `source_id` 时走 `candles` 视图（= `candle_versions JOIN candle_heads`），冷层也必须 JOIN `candle_heads` 过滤，否则会把同一 `open_time` 的旧版本也算进来。已核实冷层与横截面查询都做了这个 JOIN。
- **路由条件**：现为「热层没凑够 limit 就问冷档」，修掉了旧写法 `len(hot)<limit and start<hot_floor` 对「热层一行都没有的组合」的短路（会静默返回空）。
- **水位单一事实源**：读侧读归档器写的 `_state.json`，避免「归档器已推进、读侧用旧 env 水位」导致中间段静默漏读。
- **只读**：`mode=ro` + `PRAGMA query_only=ON`，不改任何库。

**边界口径差异（需知晓）**：`candles()` 用 `open_time < end`（左闭右开），而 `oi()` / `funding()` 用 `ts <= end` / `funding_time <= end`（**闭区间**）。回测侧调用时已按各自语义传参（资金费传 `win_end - 1`），实测无越界，但**两个 API 的边界语义不统一**，是将来接新调用方的隐患。

## 6. 未来函数审计（重点）

### 6.1 信号层因果性
- `compute_atr_wilder`：Wilder 递归，前 `period-1` 位 NaN，**因果**。
- `dc_high_prev / dc_low_prev / exit_*_prev`：均 `rolling().shift(1)`，**排除当根**。
- `exit_low_curr / exit_high_curr`：**故意不 shift**——因为当根 bar 收盘后该值即已可得，执行层按「收盘确认 → **下一根** 15m 生效」使用。这是「当期可得」，不是未来函数。
- OI 分位 `_current_pct_rank`：当期 rolling 分位，不 shift（附件的原始定义）。因 OI 按 as-of 对齐到 bar 收盘，故当根收盘时该分位可得。

### 6.2 信号产生时刻 vs 成交时刻（实测证据）
```
信号 bar 开盘 2026-10-09T11:00:00Z
确认时刻(confirm) = bar 收盘 = 2026-10-09T12:00:00Z   （confirm = bar_open + 1h ✔）
首笔成交 order.ts_ms = 2026-10-09T12:00:00Z           （差 = 0 秒）
```
执行层 `_prep_symbol` 用 `searchsorted(t15_sec, confirm, side="left")` 把信号落到**第一根 open_time ≥ confirm 的 15m bar**，并以该 bar 的 **open** 成交。1h bar 收盘与 15m bar 开盘严格同刻，故成交价是「信号已知之后」的第一个可成交价。**无未来函数。**

### 6.3 执行层因果性
- 跳空退出（相位 B）**只用 open**，不用当根 high/low。
- bar 内止损（相位 D）用当根 low/high，但发生在开仓之后，且退出释放的现金不可能被同根开仓使用（开仓在相位 C 已完成）。
- 资金费结算（相位 A）用 `(entry_ms, t_ms]` 的真实事件，`t_ms` 是当根 bar 开盘毫秒。

### 6.4 一处口径边界（低风险）
预热过滤判据是 `confirm_time < trade_start_sec` ⇒ 丢弃。**恰好等于** `trade_start_sec` 的信号**不被丢弃**：即「最后一根预热 bar（其收盘正好落在 win_start）」的信号，可以在窗口首根 15m 开仓。

- 该 bar 在 win_start 已收盘，信号已知，**不构成未来函数**；
- 但「预热不交易」的**准确表述**应是「确认时刻 < win_start 的信号不交易」，而非「预热 bar 的信号都不交易」。
- 本 run 未触发（首笔成交在窗口内 12h），属口径表述问题，非缺陷。

## 9. 仓位计算

```python
qty = min( risk_per_trade × mtm / unit_risk ,          # 风险预算
           mtm × max_leverage_per_symbol / entry_fill,  # 杠杆上限
           avail_notional / entry_fill )                # 组合保证金上限
unit_risk = |entry_fill − stop_fill| + (entry_fill + stop_fill) × fee
stop_fill = stop_ref × (1∓slip)
```
- 风险用**入场成本口径**（`entry_price → current_stop`），**不含浮盈**——修掉了旧稿「浮盈越大反而放行更大仓位」的缺陷。
- 入场前做四道拒绝：`duplicate_symbol_active`、`max_concurrent_trades_reached`、`portfolio_risk_cap_exceeded`、`portfolio_margin_cap_exceeded`，另有 `open_gapped_beyond_stop` / `nonpositive_equity` / `zero_unit_risk`。
- 实测：单笔最大名义 ≈ 79,576（≈ 权益 79.6%），未用满 2× 杠杆。
- ⚠️ 本 run 是**单标的**，`max_concurrent_trades=3` 实为死参数（同时最多 1 仓）；`rejected ×5` 全部是 `duplicate_symbol_active`。这属设计，但需知晓「3 并发」在本 run 未生效。

## 10. 「32 项恒等式」到底是什么

**它不是 32 条数学恒等式，而是 `verify_run_ledger.py` 的 32 个独立核验判据**（32 PASS / 0 FAIL）。该脚本**不复用回测运行器的任何指标/资金费函数**，只读账本行 + 原始毫秒快照做纯算术复算。逐项如下：

| # | 判据 | 内容 |
|---|---|---|
| 1 | ① | 逐笔 `net = gross − entry_fee − exit_fee − funding` |
| 2 | ② | 逐笔 `funding_fee == Σ(该笔逐事件 amount)` |
| 3 | ②b | 逐事件时间 ∈ `(entry_ms, exit_ms]` 且事件计数一致 |
| 4 | ③ | **独立**从原始毫秒快照重算逐笔资金费 == 账本 `funding_fee`（含计数） |
| 5 | ③b | 独立重推「应有结算数」== run.json `expected_settlements` |
| 6 | ③c | 每个应有网格时刻都有真实 settled 事件命中（非仅比次数） |
| 7 | ③d | 窗口左端点恰在结算网格上时**不得漏算**该笔 |
| 8 | ④ | **现金恒等式** `final_cash == init + Σgross − Σentry − Σexit − Σfunding` |
| 9 | ⑤ | **权益恒等式** 末点 `total_equity == init + Σnet`（无未平仓） |
| 10 | ⑥ | 权益曲线等间隔 15m |
| 11 | ⑥b | 首点 == 初始权益 & 末点 == final_equity |
| 12 | ⑦ | 净收益率 % |
| 13 | ⑦b | 最大回撤 %（峰含初始权益） |
| 14 | ⑦c | 交易数 |
| 15 | ⑦d | 胜率 |
| 16 | ⑦e | profit_factor |
| 17 | ⑦f | 平均盈亏比（与 profit_factor 分列） |
| 18 | ⑦g | run.json 自带「账本重算指标」且标记一致 |
| 19 | ⑦h | `open_positions_last` == 末行持仓数（≠ 整段持仓行数） |
| 20 | ⑧ | 预热不交易（全部成交在窗口内） |
| 21 | ⑧b | 窗口外信号未被交易 |
| 22 | ⑧c | 每笔 `trade.signal_id` 可联结回 `signals` 表 |
| 23 | ⑨ | 输入快照文件 SHA256 == manifest 记录 |
| 24 | ⑨b | 代码 SHA == 账本 meta == manifest |
| 25 | ⑨c | 代码 hash 覆盖后端文件 |
| 26 | ⑩ | `quality=ok` ⇒ 覆盖/对账/指标一致全部为真 |
| 27 | ⑪ | 同成本基准存在且逐点长度 == 权益曲线 |
| 28 | ⑪d | 基准末点 == final_equity（含出场滑点/费） |
| 29 | ⑪e | 基准 `net_return_pct` 与末点自洽 |
| 30 | ⑪f | 基准回撤在**含末点**的同一序列上算得 |
| 31 | ⑪b | 图表信号 `confirm ∈ [win_start, win_end)` |
| 32 | ⑪c | 图表无止盈规则时显式声明 |

> 真正的**数学恒等式**只有 3 条：① 逐笔净利、④ 现金、⑤ 权益。其余 29 项是「一致性/纪律/覆盖/可追溯」判据。README 用「32 项恒等式」统称，容易让人误以为有 32 条数学等式。

## 11. 发现的问题（按严重度）

### 🔴 中 · 发现 1：`oi_quality` 是「帧级标量广播」，每行标签失去分辨力
`factors.compute_oi_factors` 末尾：
```python
if all_nan:   out[C_QUALITY] = QUALITY_INSUFFICIENT
elif any_nan: out[C_QUALITY] = QUALITY_PARTIAL     # ← 整列赋同一个标量
else:         out[C_QUALITY] = QUALITY_OK
```
`out[C_QUALITY] = <标量>` 把**整列**写成同一个值。实测：`signal_frame` 414 行**全部** = `partial_insufficient_history`；但其中 `oi_resonance_available=True` 的有 **199 行**，12 条窗口内信号里 **11 条** 的 OI 因子其实可用（`oi_resonance_score` 有值）。

后果：`oi_quality` **无法区分**「信号在因子完整可用时触发」与「因子缺失时触发」。
连带影响：Golden README「已知限制 #2：30 条信号 `oi_quality` 全为 `partial_insufficient_history`（OI 因子历史不足）」的**归因不准确**——对 11/12 条窗口内信号，因子并非历史不足，而是标签被帧级广播覆盖。

- 严重度：中（不影响数值结果，但**误导证据判读**；「因子是否可用」这条关键证据因此不可用）。
- 建议（不在此次改动）：把 quality 改为**逐行**判定（按 `avail[i]`），或另存一列 `oi_quality_row` 与帧级 `oi_quality_frame` 并存。

### 🟠 低 · 发现 2：README 的退出原因与机器可读 golden 不一致
`README.md §3.3` 写 `trades.exit_reason: intrabar_stop 6 | segment_end_force_close_last_15m_close 1`；
`ledger_summary.json` 与账本实体均为 `intrabar_stop 6 | force_close_eod 1`。
文档陈旧（疑似沿用旧版本命名）。以机器可读为准。

### 🟠 低 · 发现 3：「可复现」是内容等价，非输入逐字节等价
- 原始 run 用 `auto_recent_days` 窗口（**末端随运行时刻漂移**，本身不可复现）；
- 复跑用**显式窗口**，故 `input_sha256` / `signal_frame_sha256` / `data_end_ms` 必然不同（已在脚本「已知口径差」声明）；
- 且 §2.3 指出：**信号序列会拉到"数据末端"**，若行情库在两次运行间增长，信号快照就会变。

结论：Golden 的等价性依赖「交易窗口被 exec 序列钉死 + 逐笔内容比对」，**不是**输入哈希等价。作为回归基准可用，但必须在文档里把这条讲透，并建议**同时固化 `sig_end_ms`/数据末端**，否则「同一显式窗口」在不同日期复跑仍可能产生非零 diff（虽不影响交易结果）。

### 🟠 低 · 发现 4：策略同名因子在本 run 中完全未参与决策
`oi_min_resonance = 0.0` ⇒ 因子门槛**未启用**，`oi_gate_enabled=false`（已在 `data_quality` 如实披露）。即本 run 实际是「唐奇安突破 / Spring / SC / LPS」四类信号的纯多头突破系统，**「OI 共振」只做证据记录、不拒单**。评估策略时不得把本 run 当作「OI 共振策略」的成绩。

### 🟠 低 · 发现 5：预热边界判据为 `<` 而非 `<=`（口径表述）
见 §6.4。不构成未来函数，但「预热不交易」的准确表述需修正。

### ⚪ 观察 · 发现 6：其它
- 建档时 `dirty_tracked_files=107`（工作树不干净）。代码身份以 `code_sha256` 为准、与 git commit 解耦——**这个设计是对的**，但需在流程上强制「以哈希为准」，避免有人用 commit 比对。
- `candles` 与 `oi`/`funding` 的区间边界语义不统一（左闭右开 vs 闭区间），见 §4。
- 单标的 ⇒ `max_concurrent_trades=3` 是死参数。

## 13. 结论与建议（不改代码，仅建议）

1. **这份 PASS 的"可信"是有限度的、但方向上可信**：账本自洽、无未来函数、成本口径正确、32 项独立核验通过、代码身份可复算——这些都是**实测**结论，不是自报。
2. **但它不是"策略有效"的证据**：7 天 / 7 笔 / 0 胜 / 因子门槛未启用。任何绩效解读都必须先排除这一点。
3. **需要修的口径问题（按优先级）**：
   - P1：`oi_quality` 逐行化（发现 1）——否则「因子可用性」这条关键证据永远读不出真实分布；
   - P2：README §3.3 退出原因订正（发现 2）；
   - P2：Golden 文档补「内容等价 vs 输入等价」的边界说明 + 固化数据末端（发现 3）；
   - P3：预热边界表述改为「确认时刻 < win_start」（发现 5）；
   - P3：统一 `candles` 与 `oi`/`funding` 的区间边界语义（发现 6）。
4. **Golden 证据清单**（§12）中，唯一缺项是 #18（`oi_quality` 逐行），其余已齐备。
