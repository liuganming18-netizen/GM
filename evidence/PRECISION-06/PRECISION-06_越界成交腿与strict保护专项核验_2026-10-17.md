## 0. 三句话结论

1. **「8 条中仅拦 1 条」是真的，而且不是 8 条。** PRECISION-05 圈的 6 个 run 共 **12 条腿**，其中 **8 条越界**，strict 只拦下 **1 条**（SPACE 的零价卖出，12.5%）。把范围放到全池（31 个有成交的 run / 62 条腿），越界是 **27 条**，strict 只拦下 **2 条**（7.4%）。

2. **越界 100% 由「取整」造成，不是撮合、不是滑点。** 8 条越界腿里滑点贡献 **0**（只有 AIGENSYN 出场带 0.02%），取整贡献 **100%**；滑点恒为 ±3bps（价格的 0.03%）。步长与价格之比最高到 **1.475**（SPACE 出场：步长比价格本身还大），最低 0.117（COTI 出场）。

### 1.3 三个必须先讲清楚的口径

**口径 A：`price_step` 不是记录值，是算术反推值。**
`inputs.json → fingerprints.config.params` 的 49 个键里**没有** `price_step` / `tick_size` / `instrument_spec`；27 个修复前 run 也**没有** `instrument_spec.json`。所以「运行时用的步长」只能反推：对每条腿枚举 `0.01 / 0.001 / 1e-4 / 1e-5 / 1e-6 / 1e-7`，看哪个能**逐位复现**记录成交价，再取同一 run 两条腿的**交集**。

反推结果：**每个 run 的交集都是单元素集**（不存在多解）：

| 步长 | run 数 | 腿数 |
|---|---|---|
| `0.01` | 27 | 54 |
| `1e-4` | 2 | 4 |
| `1e-6` | 1 | 2 |
| `1e-3` | 1 | 2 |

**这套反推方法本身是可验证的**：有 4 个 run 把步长记录进了 `summary.precision.price_steps`，反推值与记录值 **4/4 完全一致**（1e-6 / 1e-4 / 1e-4 / 1e-3）。所以在没有记录的 27 个 run 上，`0.01` 这个结论的可信度不是「猜」，而是「同方法在有真值的样本上全对」。

`inside_bar = low ≤ 成交价 ≤ high`，用的是 `trades.jsonl` 里的成交价和 `chart.json` 里同刻 15m K 线，不依赖步长假设。所以「27/62 条腿越界」这个数字**不依赖口径 A**。

**口径 C：术语修正 —— 不是「四笔越界成交」。**
准确的统计关系是：

| 层级 | 数量 | 说明 |
|---|---|---|
| P05 圈定的 run | 6 | SPACE / AIGENSYN / TRUTH / COTI / BNB / ORDI |
| 其中的成交 | 6 笔 | 每个 run 恰好 1 笔 |
| 其中的成交腿 | **12 条** | 6 笔 × （入场 + 出场） |
| 越界的腿 | **8 条** | SPACE / AIGENSYN / TRUTH / COTI 四个标的，**每笔的开平两条腿都越界** |

### 3.4 现有成交模型是否允许这种越界？允许，而且是结构性的

`SimulatedBarFillAdapter` 的成交模型只有三步：**取 bar 的 open（或止损价）→ 加/减滑点 → 按步长向最劣方向取整**。它**没有**「结果必须落在 bar 区间内」这一步，也不可能有 —— 因为 `FillAdapter` 协议（`fill.py:179-183`）的入参只有：

```python
def quote_entry(self, *, raw_price: float, direction: int, price_step: float,
                stop_price: float) -> FillQuote: ...
def quote_exit(self, *, target_px: float, direction: int,
               price_step: float, reason: str) -> float: ...
```

**没有 `bar_low` / `bar_high`**。所以「成交价必须落在 K 线区间内」这条约束，在**架构上就没有位置**可以放。这是本次最重要的结构性发现：不是忘了写检查，是接口里没有这个信息。

引擎侧（`engine.py`）**手上有** hi/lo（相位 D 的 `hi, lo, cl` 就在 647 行），但成交后只做记账，**没有任何比较**。

### 3.5 哪些越界是「模型允许」的，哪些不是

不能默认所有越界都要拒。按「越界量能不能被模型自己的假设解释」分三类：

| 类别 | 判据 | 本次实例 | 该不该拒 |
|---|---|---|---|
| **A. 取整导致** | 越界量 > 滑点允许量（`slip_rate × raw`） | 8 条（P05 范围）/ 25 条（全池） | **必须拒**（结构性错误） |
| **B. 滑点导致** | 越界量 ≤ 滑点允许量 | XMR 出场（0.037%，其中滑点 80%）、SOON 出场（2.8%，滑点 1.1%） | **不该拒**（模型假设，3bps 是刻意的保守） |
| **C. 零价** | 成交价 ≤ 0 | SPACE 出场、TAG 出场 | **必须拒**（经济上不可能，已由 R5 拦下） |

XMR 的例子最能说明问题：它的 bar low 恰好等于开盘价，3bps 滑点把卖出价推到 low 之下 0.04，再叠加取整 0.0098，总越界 0.05。**滑点那 0.04 是模型故意保守，不是错误；取整那 0.0098 才是误差。** 所以闸门必须带「滑点允许量」这个容差，否则会把正常成交一起打掉。

### 3.6 strict 的职责到底是什么

| 维度 | strict 管不管 | 依据 |
|---|---|---|
| 价格合法性（有限、> 0） | **管** | R1、R2 |
| 步长合法性（有限、> 0） | **管** | R3、R4 |
| 取整结果为正 | **管** | R5 |
| 规格一致性（step 是否等于 spec.tick） | **不管** | 只接受调用方传值，不比对 spec |
| 成交区间约束（∈ bar[low, high]） | **不管** | 协议里没有 bar |

所以「strict 只拦 1 条」不是 strict 失职 —— **它从来没被要求管这件事**。真正该管的两件事（R7 区间、R8 规格）一个都没实现。

### 5.2 整改 1（P0）· `fill.py` 加 R6：步长不得粗于价格

**根因与位置**：`策略/WyckoffMaster/trading_core/fill.py:238-241`，`_guard` 在 `if step <= 0` 之后。

**最小改动范围**（约 8 行，只加一个分支，不动任何既有分支）：

```python
        if step <= 0:
            raise FillRejected("invalid_price_step_nonpositive",
                               {"price_step": str(price_step), "stage": kind,
                                "raw_price": str(raw)})
        if step > raw:                       # ← 新增：步长粗于价格 ⇒ 每一档都跨过整个价格
            raise FillRejected("price_step_coarser_than_price",
                               {"price_step": str(step), "raw_price": str(raw),

```

**预期行为**：
- `step > raw` ⇒ `FillRejected('price_step_coarser_than_price')`，带 `raw_price` / `price_step` / `stage`。
- 入场被拒 ⇒ 不生成成交、不建仓；出场被拒 ⇒ 仓位保持未平。

**验收案例**：`FIX_01`（现在 xfail，整改后应转绿）。

**R6 单独不够**（只拦 2/8），但它是零误杀的第一道闸，且**能让 R5 的零价分支在 strict 下不再可达**（零价必然要求 `raw < step`）—— 也就是说 R6 是「根因闸」，R5 是「症状闸」。

### 5.3 整改 2（P0）· `engine.py` 加 R7：成交价必须落在该 bar 区间内

**根因与位置**：`策略/WyckoffMaster/trading_core/engine.py` 的 4 个成交点：

| 相位 | 行 | 现有 hi/lo 可用性 |
|---|---|---|
| B 跳空/到期出场 | 385-388 | 有（`arr["open"][i]`，同 bar 的 high/low 可直取） |
| C 新开仓 | 448-451 | 有 |
| D bar 内止损 | 658-661 | **已在作用域内**（`hi, lo, cl`，647 行） |
| E 期末强平 | 720-723 | 有（最后一根 bar） |

**最小改动范围**：新增一个模块级 helper（约 15 行）+ 4 处调用（每处 3–5 行）：

```python
def _assert_fill_in_bar(*, fill, raw_price, bar_low, bar_high, slip_rate, stage):
    """成交价必须落在该 bar 区间内；容差 = 滑点允许量（不含整档）。"""
    allow = abs(float(raw_price)) * slip_rate
    if not (float(bar_low) - allow <= float(fill) <= float(bar_high) + allow):
        raise FillRejected("fill_outside_bar_range",
                           {"fill": repr(float(fill)), "bar_low": float(bar_low),
                            "bar_high": float(bar_high), "allowance": allow,
                            "stage": stage})
```

**为什么容差用「滑点允许量」而不是「1 个整档」**：加一个整档会把 SPACE 这种「步长 = 1.03 × 价格」的越界洗成合法（越界量 0.000279 < 1 档 0.01）。用滑点允许量才能把 M1（XMR 0.037%，滑点占 80%）留下、把 A（取整）拦掉。实测：**R7 拦下 27/27，误伤 0/35**。

**预期行为**：
- 越界腿被拒 ⇒ 该腿记 `rejected_orders`（reason `fill_outside_bar_range`）+ 写 `invalid_reasons` ⇒ `run_valid=False`。
- 入场被拒 ⇒ 不建仓；出场被拒 ⇒ 仓位保持未平（沿用现有语义）。

**验收案例**：`FIX_02`（现在 xfail，整改后应转绿）。

**影响面**：`GUARD_01`（真实 tick 下正常成交）、`GUARD_02`（零价）、`GUARD_03`（缺规格）都必须保持绿。实测在 12 条腿与 62 条腿上，R7 对**区间内**的腿**零拦截**。

### 5.4 整改 3（P1）· 入场精度拒绝也要影响 `run_valid`

**根因与位置**：`engine.py:886` `"run_valid": not invalid_reasons`，但入场侧三个拒绝点（452-462 价格、537-543 数量、554-558 名义额）都**不写** `invalid_reasons`。

**为什么必须做**：影子实测显示，加了 R6 之后 SPACE 场景变成「入场被拒、0 成交、`run_valid=True`」—— 比现在更危险，因为**一个什么都没跑成的 run 看起来是「有效」的**。

**预期行为**：任何因精度原因被拒的入场 ⇒ `run_valid=False`，`invalid_reasons` 非空。

**验收案例**：新增（建议并入 `FIX_02`）：入场被拒时 `run_valid is False`。

**内容**：`step > 1% × raw` ⇒ 拒绝。**实测不建议单独用**：
