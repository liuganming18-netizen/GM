## 1 底层为什么是「明确不可正式通过」

`formal_pass_allowed` 只有一个赋值点：

```python
# instrument_spec.py:1022
"formal_pass_allowed": applicability == APPLICABILITY_VERIFIED,
```

而 `verified` 的成立条件是（`instrument_spec.py:944-970`）：窗口被**两份数值一致的快照夹住**
（一份早于窗口起点、一份晚于窗口终点），且变更证据覆盖整窗。

现有证据只有两份 `exchangeInfo`：

| 文件 | serverTime | 结论 |
|---|---|---|
| `exchangeInfo_futures_2026-10-05T015512Z.json` | 1790941589240（2026-10-02T11:46:29.240Z） | 晚于全部历史窗口 |
| `exchangeInfo_futures_2026-10-05T045328Z.json` | 1790941589242（…29.242Z） | 同一时刻的另一次响应（差 2 ms） |

两份都在 2026-10-02，**都晚于** 2024–2025 的回测窗口 ⇒ 夹不住任何历史窗口 ⇒ 结构性地
`formal_pass_allowed = False`。这不是「某个标的运气不好」，是**全池 375 个窗口一律 False**。

> 附带纠正一处既有说法：这两份快照的 `serverTime` 相差 2 毫秒（不是完全相同），
> 哈希也不同（`07445c2f…` vs `e0ecf7bd…`）。但 2 ms 属同一时刻，结论不变。

证据：`规格适用性分布.json`（逐 run 明细）、`运行输出.txt` 第 3 段。

## 4 重点 2：「程序运行完成」与「研究验收通过」

现状是**两者被同一个词承载**：

- `status` 枚举只有 `queued|running|succeeded|failed|interrupted`，`succeeded` 的含义严格来说是
  「执行器没抛异常」。`execute_run` 的实现就是 `try: _run(...) except: failed; else: succeeded`
  （`backtest_runner.py:1410-1424`）。
- 唯一带「验收」语义的 `formal_run_gate()` 是**模块级静态常量**，与 run 无关，而且
  `G01–G03` 写死 `pass`。
- 页面上唯一提示「执行完成 ≠ 正式放行」的那句话，在**默认折叠**的 `<details>` 里
  （`BacktestWorkbench.tsx:2355-2371`），且旧 run 的 `formal_m4_gate` 为 `null`，展开也只看到
  「未取到 ⇒ 不推断已放行」。

所以现在的实际观感是：**绿色 succeeded + 绿色「质量：通过」= 用户认为结果可用**。
而 `precision.run_valid=False`（出场被拒、仓位未平）这种情况，页面上表现为
「0 笔交易 + 一个收益率」，**没有任何标记**。

## 6 重点 4：375 个旧结果怎么显示「历史规格未核验」

**原则：不重跑、不回填、不伪造。缺失就是缺失，但要显式说出来。**

判定规则（三态，可判定、不需推断）：

| 磁盘事实 | 显示 |
|---|---|
| `summary.json` 有 `formal_pass_allowed=true` 且 `instrument_spec.applicability="verified"` | 规格：已核验 |
| 有字段但 `false`（含 `unverified_historical/contradicted/not_listed/missing`） | 规格：未核验（附 `applicability` 原因码） |
| **字段不存在**（= 375 个旧 run 的全部） | **规格：未记录（历史结果，生成时无此字段）** |

最小改动（只加字段、不改语义）：

1. `backtest_store._summary_to_run_doc` 增加一个 `spec_verification` 块：
   `{"status": "not_recorded"|"verified"|"unverified_historical"|..., "source": "summary.json", "reason": ...}`
   —— **不动** `status`、**不动** `data_quality.status`（那两个是执行/数据语义，混进来会污染既有判据）。
2. 前端把绿色「质量：通过」文案改成「运行完成 · 数据自检一致」，并**并列**一个独立徽标
   「规格：未记录 / 未核验」（灰/黄，不用绿）。
3. `qualityOk`（决定绿色）追加一条：`spec_verification.status === 'verified'`。
   这样 375 个旧 run 会立刻从「绿色通过」变成「运行完成 · 规格未记录」，**不需要重跑任何一个 run**。
