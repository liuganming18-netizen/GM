## 8. 用户逐项审核流程与回执模板

1. 本项先固定源真实文件名单/备份截点和目标，记录预计容量、现有目标冲突及写者。
2. Work只迁本项，逐文件校验或SQLite在线一致快照；保留断点和原件。
3. 交回执`docs/迁移回执/<编号>_<名称>.md`及`evidence/迁移/<编号>/`机器证据；状态为**等待用户审核**。
4. Codex整理证据/指出差异，**用户亲自给通过或退回**。未回复、工具exit 0、Work自报完成或Codex意见均不能代替用户决定。
5. 用户明确“本项通过，继续下一项”后，新Work窗口做下一项；用户退回时仅整改本项。任何缺失/容量不足/冲突都停在本项，不越过。
6. 只有所有必要数据/源码项分别通过后，才另审生产配置切换；到此为止旧生产写入仍保留。历史源删除没有授权。

每项回执必须包含：

| 必填字段 | 用户可核对内容 |
|---|---|
| 编号/名称/角色 | 与总清单一致；是正式库、原件、备份、代码还是历史研究 |
| 源与目标 | 完整绝对路径；来源文件名单/源版本/目标冲突 |
| 迁移前后数量 | 文件数、ZIP数、CHECKSUM数、SQLite表数/行数、Parquet分片/行数；同口径对比 |
| 迁移前后大小 | 逻辑字节、实际盘占用/空闲盘；持续变化文件的查询/快照时点 |
| 内容与时间 | SHA/schema/主键/单位/周期/交易所/合约代际/最早最新/可得时间及实际SQL |
| 完整性与差异 | 校验结果、未迁/错误/缺口/重复/官方不可得；不能unknown写0 |
| 操作和运行 | 实际工具/命令、PID/退出、断点、源数据保持状态、是否切流（本阶段为否） |
| 人工决定 | 用户审核：未审核 / 通过 / 退回；用户原话与时间；不代填通过 |
