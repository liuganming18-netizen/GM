# PC4 BUG 修复：REST 补口入库器返回契约（阻断六周期导入）2026-10-08

## 1. 现象（实测，非推测）

首次启动六周期串联后，`1d/archive_import` **exit=5**，`batch_state/1d.json` 中 `BTCUSDT`
`failed_files=1`，文件级条目：

```
batch_state/1d/BTCUSDT.json  key=rest|binance|BTCUSDT|1d|1567900800000
status=import_failed
note=ValueError: not enough values to unpack (expected 3, got 2)
```

**这不是数据缺失**：BTCUSDT 1d 的 2019-09-08 起头段**早已在库**（`first_open=2019-09-08T00:00:00Z`），
该 REST 条目只是阶段 A 落盘的**同一批根**的正文证据。

## 2. 根因

`logs/_pool_restfill.py::import_rest()` 在「本批根**已全部在库**」这条正常幂等路径上：

```python
missing = [(o, r) for o, r in rows if int(o) not in have]
if not missing:
    return 0, None          # ← 只返回 2 个值
```

而所有调用方（`batch_download._import_rest_entry`、`_pool_restfill.main`）都按
`added, sid, ev = import_rest(...)` **解包 3 个值** ⇒ `ValueError`。
该异常被 `batch_download.import_symbol` 的 `except Exception` 捕获后记为 `import_failed`，
导致该周期 `failed_files≥1` ⇒ 阶段状态 `failed` ⇒ 批量退出码 **5** ⇒ 按串联纪律停止后续周期。

影响面：任何「REST 落盘的根此前已由归档入库」的标的都会命中（BTCUSDT 头段是典型）。

## 3. 修复（最小改动，只改返回契约）

```python
if not missing:
    return 0, None, "no_rows"
```

语义与其它路径一致：`added=0`、`source_id=None`、`evidence_status="no_rows"`。
调用方 `import_symbol` 对 `ev in ("linked","no_rows")` 且 `added==0` 记 `already_imported`（幂等复用），
**不再误报失败**。未改动限频/证据闸门/写库结构/任何判据。
