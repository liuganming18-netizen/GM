### 二、方向字段契约（供前端沿用）

`/api/v1/markets`、`/api/v1/markets/{exchange}/{market_id}` 的每个 item：

| 字段 | 类型 | 取值 | 语义 |
|---|---|---|---|
| `signal_direction` | `"long" \| "short" \| null` | **只认这两种** | 该标的**最近一条真实信号**的方向；无信号 = `null` |
| `signal_status` | `string \| null` | `candidate` / `waiting_retest` / `confirmed` / `invalidated` / `expired` / `undecided` | 同上那条信号的状态；不在枚举内 = `null` |
| `signal_ref` | `object \| null` | 见下 | **仅在有信号时出现**，供核对来源链 |

```jsonc
"signal_ref": {
  "signal_id": "123", "strategy_key": "A", "strategy_version": "…",
  "config_hash": "…", "timeframe": "4h",          // 只在 TF_SET 内才给，否则 null
  "status": "confirmed", "direction": "long",
  "event_time": "2026-10-05T04:00:00Z",           // 事件时点（bar 收盘）
  "confirmed_at": "2026-10-05T04:00:00Z",         // **确认时点**，不回填
  "data_version": "dv:…"
}
```

**取值口径**：按 `confirmed_at DESC, id DESC` 取该 `(exchange, symbol)` 的 **top-1**，
即「最近被确认的那条」；与 `/api/v1/signals` 的排序一致。窗口函数取 top-1，不全表读入。

**纪律（不可放宽）**：
- 方向**只能**来自 `signals` 表（A/B 策略事件）。**禁止**用 24h 涨跌、taker 买卖比、
  人数多空比、资金费率等派生量推导方向。
- 脏值（如 `direction="bullish"`）**一律回 null**，不透传。
- `signals` 表不存在 / 为空 → `null`，不报错、不造值。

### 一、故障现象（主助手 16:47 报告，本轮独立复现）

| 现象 | 复现结果 |
|---|---|
| 页面「数据状态未取得」 | `/api/v1/pool/status` **>20s 超时**（http=000） |

| 日志 | `logs/backend.log` 内 **561 次 `BrokenPipeError`**（客户端超时断开，服务端仍在处理） |

### 二、根因（逐层取证，非猜测）

**① 数据库本身是健康的** —— 用**独立新进程**直接调用同一份 `adapter.py`：

```
covered() 0.064s | sources_index() ~0.2s（第二次）| pool_index() 0.207s
realtime_index() 0.009s | oi_latest_index() 0.010s | funding_latest_index() 0.150s
signal_latest_index() 0.001s | cls_index() 0.008s | workbench_scope() 0.017s
→ v1_markets() 6.79s，total=549，items=549   ✅ 能返回
```

`candles` 是**视图**（底层 `candle_versions` + `candle_heads`，走 `sqlite_autoindex`），
单标的查询 **0.000s**；`sources` 表 50,678 行全表扫描 **0.226s**。**库不慢，慢的是那个进程。**

**② API 进程（PID 28971）文件描述符泄漏 —— 这是真因**

```
lsof -p 28971 | wc -l                     → 3,589 → 3,981 → 4,922 → 4,984（持续上行）
其中 DB 相关 FD                            → 2,045（主库 1,168 + WAL 1,166）
lsof -a -p 28971 -i | wc -l                → 1,197 个 socket，绝大多数状态为 CLOSED
```

即：**已完成/已关闭的 TCP 连接与 SQLite 连接的 fd 从未释放**，随每次请求累积。

**③ 泄漏的连接钉住了 WAL → WAL 膨胀到 620 MB**

```
market.sqlite3-wal = 620,121,832 B（163,283 帧）；-shm = 1.2 MB
PRAGMA wal_checkpoint(PASSIVE) → (busy=0, log=163283, checkpointed=11910)   # 只能推进 7%
```

泄漏的长事务读者使 checkpoint 无法回收 WAL → 每次查询都要穿过 620 MB 的 WAL →
**所有请求整体变慢** → 前端轮询不断堆叠 → 线程/socket 更多 → 更慢。
**这是典型的死亡螺旋**：`6.8s → >30s`。

**④ 次要放大因素**：`Handler` 未设 `timeout`。`BaseHTTPRequestHandler` 默认无读超时，
客户端（前端 dev proxy 的 keep-alive 连接）不再发数据时，处理线程会**永久阻塞**在
`rfile.readline()`，socket fd 与线程无界累积——正是 ② 的成因。

### 三、修复（仅本项目 API，最小改动）

| 代码护栏 | `adapter.py` → `class Handler` 新增 `timeout = 30`（连接级读超时，超时即 `close_connection` 正常收尾）。**只影响空闲连接，不改任何接口契约与响应内容** |
| 重启 | 身份校验（`lsof` cwd == 本后端目录）通过后 `sh stop.sh` → `sh start.sh`。**只重启 8787 这一个进程** |

**未做**：不重复启动健康采集、不终止/重跑历史下载、不删任何数据、不改前端、
不改策略判据、不新增研究或策略功能。
