## 三、根因：7 个批量脚本把 4 个字段写死

`run_batch_round6_100.py::generate_chart_payload()`（第 97–114 行）：

```python
chart = {
    ...
    "candles": candles,          # ← 数组格式 [t,o,h,l,c,v]（后端写的是对象）
    "signals": [],               # ★ 写死为空
    "trades": trades,            # ← trade_id 直通 t.get("trade_id") ⇒ null
    "equity_curve": equity_curve,
    "funding_events": [],        # ★ 写死为空
    "benchmark": {"symbol": symbol, "return_pct": 0.0, "equity_series": bench_series},  # ★ return_pct 写死 0.0
}
with open(chart_path, "w") as f:
    json.dump(chart, f, ensure_ascii=False)   # ← 紧凑格式（后端 _write_json 是 indent=2）
```

全量实测（344 个 `run_WX_EVENT_TREND_V0_1_*/chart.json`）：

```
candles 数组格式 : 344 / 344
signals 为空     : 344 / 344
trade_id 为 null : 23 笔
```

**这些字段的真实数据一直都在同目录里**：`candidates.jsonl`（候选）、`funding.jsonl`（资金费）、`trades.jsonl`（trade_id）、`equity_curve.jsonl` + K 线（基准收益）。脚本只是没去读。

### 连带：`/equity` 与 `/backtests` 也有同样的写死

- `/equity` 的 `benchmark.return_pct` = `0.0`，而 `benchmark_equity` 曲线是真的（2000 → 1004.89，即 **−49.76%**）。
- `/backtests` 的 `max_drawdown_pct` = `0.0`（**200/200 条全是**）。`_summary_to_run_doc` 里写的是
  `float(summary_data.get("max_drawdown_pct") or 0.0)`，而包的 `summary.json` **根本没有这个字段**
  ⇒ 「没算」被伪装成「回撤 0%」。这违反项目自己的纪律「缺结果一律 None，不用 0 冒充」。

## 四、回答「这个回测 AI 会不会造假」

分两层说，不含糊：

### 4.1 计算结果层：**改不了，或者一改就露**

1. **AI 不参与计算**。回测是 `框架/backend/backtest_runner.py` + `策略/WyckoffMaster/event_trend_v0_1/` 的
   Python 程序跑的，输入是交易所 Parquet，输出落盘。语言模型不在计算链路上。
2. **可对回源**。K 线逐根能对回交易所原始 Parquet（2.3 节实测一致）；成交价必须落在对应 K 线区间内（2.4 节）。
3. **可复现**。同规格重跑数值完全一致（2.5 节）。想改一个数，就得同时改权益曲线、逐笔、账本、
   `validation_results`，还要让 `identity.chain_ok` / `reconcile.cash_identity_ok` 继续成立——
   而这几个自检本身就在 `summary.json` 里，改一处就对不上另一处。
4. **有哈希清单**。每个 run 目录的 `manifest.json` 记录 15 个文件的 sha256；`inputs.json` 记录
   策略代码指纹 `code.combined_sha256`。

**但要说清楚边界**：`summary.json` 里的 `identity` / `reconcile` 自检是**回测程序自己写的**。
一个从一开始就造假的程序，它的自检也会一起造假。真正能证伪的是 **2.3（对回源）+ 2.5（可复现）**，
不是自检本身。这也是为什么「对回交易所 Parquet」这一步必须做。

### 4.2 界面字段层：**确实被写死过，这次修的就是它**

`signals: []`、`funding_events: []`、`benchmark.return_pct: 0.0`、`trade_id: null`
—— 这四个**不是算出来的，是手写的常量**。

- 它们**没有伪造盈亏**（净收益、逐笔、K 线都是真的）；
- 但它们**让界面说了假话**：净值对比图上「基准收益 0.0000%」是假的（真实 −49.76%），
  「本 run 无信号」也可能是假的（实际有 1 个候选）。
- **这是真实存在的问题，我不替它遮掩。** 它的成因是「为了批量出图，写了个绕过账本和接口的
  临时脚本」，不是「AI 编造业绩」。

一句话：**业绩没造假，界面有假字段。前者靠可复现+可对回源守住，后者这次已经堵上。**

## 五、本次修复（3 处，均在读取侧；**不写死、只从本 run 自己的落盘文件取数**）

### ① `backtest_api.py::get_chart` — 新增 `_backfill_chart()`

对**所有** run（旧 344 条 + 新的）在读取时补全：

| 字段 | 来源 | 规则 |
|---|---|---|
| `signals` | `candidates.jsonl` | `t = available_at_ms`；`atr = box_atr_a`；`oi_score = oi_growth_6h`。仅在现有 signals 全无效（空或 `t<=0`）时覆盖 |
| `trades[].trade_id` | `trades.jsonl` | 按 `(entry_time, exit_time)` **毫秒对齐**换回，不按顺序硬套 |
| `benchmark.return_pct` | `benchmark.equity_series` + `equity_curve` 起点 | 取不到才退回 K 线首开→末收 |
| `funding_events` | `funding.jsonl` | `amount = payload.delta`；`rate`/`mark` 本 run 未落盘 ⇒ 保持 `None` |

**纪律**：`candles` / `equity_curve` 一律不动；取不到就保持原样（宁可空着，不造数）。

### ② `backtest_api.py::get_equity` — 基准元数据补全

从真实 `benchmark_equity` 序列取末点作为 `final_equity`，以策略起点权益为基数算
`net_return_pct`（同本金口径）。修掉「曲线是真的、标签写 0」的矛盾。

### ③ `backtest_store.py::_summary_to_run_doc` — 回撤如实缺失

`float(... or 0.0)` → 缺字段返回 `None`，界面显示「—」。不再把「没算」伪装成「回撤 0%」。

### ④ 前端（`LabChartPanel.tsx` / `BacktestWorkbench.tsx`）

- **K 线补上「候选信号」标记**（箱体突破那一刻）——这是「K 线 → 逐笔」链条的第一环，
  以前图上只剩开/平仓两支箭头，看不出「为什么在这根开仓」。`t<=0` 一律丢弃，不在错位置画假点。
- **逐笔明细空态改为解释成因**：区分「有 N 个候选但未成交」与「无候选信号（箱体未有效突破）」，
  不再只写一句「后台账本为空」。

## 七、遗留（本窗口未动，需你决定）

1. **后端需重载一次才生效**。`adapter.py` 用的是 `ThreadingHTTPServer.serve_forever`，**没有热重载**。
   按项目约定「服务重载由『账本保全』窗口独占」，本窗口未自行重启 8787。
   入口：`停止系统.command` → `启动系统.command`（或 `框架/backend/stop.sh` + `start.sh`）。
2. **7 个批量脚本仍在写死那 4 个字段**。本次是在**读取侧**堵住的（所有 run 都受益），
   但落盘的 `chart.json` 本身仍是残缺的。建议把批量脚本改为**走后端 `POST /backtests`**，
   或至少复用后端同一个 chart 构造函数，避免再出现「两套写盘格式」。
3. **`backtest_runner.py::_run_event_trend` 有同类 bug**（该文件有并行窗口的未提交改动，本窗口未动）：
   - 第 890 行 `c.get("entry_bar_time_ms")` —— `candidates.jsonl` 里**没有这个字段**（真实是
     `execution_earliest_ms` / `snapshot_time_ms`）⇒ 信号 `t` 恒为 `0`（实测新 run 确认）；
   - 第 894/895 行 `atr_1h` / `oi_growth_pct` —— 不存在（真实是 `box_atr_a` / `oi_growth_6h`）⇒ 恒为 `0.0`；
   - 第 935 行 `summary_data.get("max_drawdown_pct") or 0.0` —— 同上「0 冒充」。
   （读取侧补全已把这些挡住，但源头仍应改。）
4. **`max_drawdown_pct` 的真实值仍未计算**。现在如实显示「—」，但要让 ⑥ 的「回撤」列有真数，
   需要在 run 产出时从 `equity_curve.jsonl` 按峰值展开算一次（本窗口未动包内 `runner.py`，
   因其规则 SHA 冻结）。
5. **candles 两种落盘格式并存**（旧 344 条数组 / 新后端对象）。前端 `normalizeCandle()` 两种都认，
   但后端两侧应统一（数组更省一半体积：2.8MB vs 4.9MB）。

## 八、环境观察

- 本窗口工作期间（08:24 建的一条 `bt_*` run）在 08:27 前后被删除；同时 runs 目录新增
  31 条 `run_WX_EVENT_TREND_V0_1_*`（标的清单与 `run_batch_round6_100.py` 的 `ROUND6_100_SYMBOLS`
  完全一致）⇒ **有另一处正在跑批量脚本**。无 crontab / launchd 定时任务，应为手动或另一窗口触发。
- 这解释了「链条时通时不通」的观感：**批量脚本每跑一轮，就用残缺的 `chart.json` 覆盖一批 run。**
