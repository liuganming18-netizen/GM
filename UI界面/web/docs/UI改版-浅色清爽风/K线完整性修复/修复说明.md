# 展开图 K 线「没有完整导入」排查与修复

**范围**：`http://127.0.0.1:3000/`（工作台 → 展开某标的的 K 线详情）
**结论**：K 线数据在后端是连续的，问题**全部在前端**——两层独立缺陷叠加，观感就是「K 线没有完整导入」。已修复。

---

## 一、现象

展开 BTC 的 K 线后，时间轴跨约 3 天，但蜡烛只画在最右侧约 4% 宽度，左侧 96% 全空。

## 二、根因（两层）

### 缺陷 1：首屏落位被「共享时间网格」的远端锚点撑宽

两图（K 线 + OI）共用同一套「时间点并集网格」：各自补**纯 whitespace 锚点**（不带数值，只为对齐逻辑索引）。
`buildGridAnchor()` 会把「只有 OI 有、K 线没有」的时点也补进 K 线图。官方库的时间轴范围取**全图所有序列的并集**，
于是 K 线图的时间域被远端锚点撑宽：

| 序列 | 跨度 | 实测 |
|---|---|---|
| K 线（1m 一页） | ≈ 8.3 小时 | 500 根 |
| OI 快照 | **4.6 天** | 323 点（2026-10-05T04:22 → 2026-10-09T17:05） |
| 并集 | **4.6 天** | ← 时间轴按此落位 |

`fitContent()` 便按 4.6 天落位 → 蜡烛被压到最右侧约 4%。

**修法**：主图（`leader`）首屏改为按**自身 K 线域**落位，不再 `fitContent()`。
`src/components/LightweightChart.tsx` → `applyInitialViewport()`：

```ts
const landedOnOwnDomain =
  member.role === 'leader' && domain
    ? applyTimeRangeTo(member, domain.from, domain.to)
    : false;
if (!landedOnOwnDomain) safeTimeScaleCall(() => chart.timeScale().fitContent());
```

时间轴点集仍是共享并集，逻辑索引对齐与跨图十字线联动全部不受影响。

### 缺陷 2：分页历史链路从未被触发 —— 展开图永远只有 60 根

`ensureDetail` 只取 `DETAIL_BAR_LIMIT = 60` 根实时尾段，而分页历史一页都没拉过。四层叠加：

| # | 事实（改前代码） | 后果 |
|---|---|---|
| ① | `loadHistoryPage(tf, true)` 只在用户手点周期按钮（`handleSelectTf`）时调用 | 自动收敛出的 `selectedTf`（正常首屏走这条）从不触发 |
| ② | 于是 `historyPages[selectedTf]` 恒为空 | `activeHistoryPage?.hasMore` 为 `undefined` |
| ③ | 「加载更早历史」按钮条件是 `activeHistoryPage?.hasMore && ...` | 按钮**永不渲染** |
| ④ | 唯一的自动补页 effect 被 `restorePendingRef` 挡住（无存档视窗时为 `false`，直接 return） | 拖动 / 缩放也不会补页 |

**后端是好的**（`curl` 直查）：

```
history_only=1&limit=500  → bars 500  has_more true  next_cursor 1791536220000
```

纯前端没请求。

**修法**：在 `src/components/InlineExpandedChart.tsx` 为「当前标的 × 当前周期」补一次首屏历史页（幂等）。

```ts
const historySeedKey = useRef<string | null>(null);
useEffect(() => {
  const key = `${token.id}:${selectedTf}`;
  if (historySeedKey.current === key) return;
  historySeedKey.current = key;
  void loadHistoryPage(selectedTf, true);
}, [token.id, selectedTf]);
```

## 三、取数口径：对齐原版实测值

原版 bundle（`tradeflow_index-27SKEJ8j.js`）实测：

```js
// 原版 K 线组件 the({symbol,markers,anchorTime}) 的取数
let g = !i || n - i >= 3e6;                  // 首次 或 距上次 ≥50 分钟 → 全量
let r = await Qme(e, g ? 1500 : 50, f.signal, m);   // 首次 limit=1500，增量 limit=50
u = $me(g ? [] : u, r);                      // $me 末尾 .slice(-1500) → 序列上限 1500 根
```

```js
// 原版图表：lightweight-charts，不设任何显式可视范围 → 用库默认 barSpacing = 6px / rightOffset = 0
```

本项目绘图区实测 **1124px（主画布）+ 84px（价格轴）** → 原版首屏可见根数 ≈ 1124 ÷ 6 ≈ **187 根**。

据此改两个常量：

| 常量 | 位置 | 改前 | 改后 | 依据 |
|---|---|---|---|---|
| `DETAIL_BAR_LIMIT` | `src/api/useMarketData.ts` | 60 | **180** | 对齐原版默认可见窗口（≈187） |
| `HISTORY_PAGE_LIMIT`（新增常量） | `src/components/InlineExpandedChart.tsx` | 500（硬编码） | **1500** | 对齐原版「首次 1500 根」 |

成本实测：单周期一页 1500 根 = **581 KB / 57 ms**（本地后端）。
（对比：若改 `DETAIL_BAR_LIMIT` 而非历史页，9 个周期 ×1500 = 5.1 MB，故只对**当前选中周期**放大历史页。）

## 五、遗留：本地 1m 归档本身有真实缺口（非 UI 问题）

分页回溯 12 页（18,000 根）实测：

| 项 | 值 |
|---|---|
| 覆盖 | 2026-09-26T18:29Z → 2026-10-09T17:22Z（**310.9 小时 / ≈13 天**） |
| 缺口 | **11 处，共缺 654 根** |
| 最大缺口 | 2026-10-07T16:56Z → 2026-10-08T01:35Z，**缺 518 根（8.6 小时）** |
| 次大缺口 | 2026-10-08T03:46Z → 05:40Z，缺 113 根 |

**已确认不是读取侧过滤**：`adapter.py` 的 `_utc_boundary_filter` 只作用于 `okx/12h`，
`lifecycle.annotate_rows` 对非 12h **只打标签不删行**（`v1_candles()` 第 1534–1557 行）。
两页拼接本身完全连续（p1 起 08:59，p2 止 08:58），故缺口是**库内真实缺失**。

UI 已如实上报（状态行「闭合段缺口 N 处（最多缺 N 根）」），**未做任何掩盖**。

**未修**，原因：补缺必须走后端统一网关（限频 / 冷却 / 请求头）。
实测经 vite `/bapi` 代理直取币安返回 **403 Forbidden**，浏览器侧不可达；
现成的 `历史下载/_rest_gap_fill.py` 只处理**归档周期级**缺口（头段 / 整月缺档），
不覆盖日内 1m 缺口。属独立的后端数据作业，待确认后再做。
